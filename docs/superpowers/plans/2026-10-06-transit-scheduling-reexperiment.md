# 경로 요청 스케줄링 재실험 Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task-by-task. 실제 외부 API 실행은 아래 사전 조건과 예산을 충족한 후 진행한다.

**Goal:** 시작 간격의 효과를 분리 측정하고, 동시 요청 상한의 필요성과 비용을 별도로 검증한다. 결과는 검증한 부하 범위에서의 운영 후보로 한정한다.

**Architecture:** 별도 로컬 실험 서버에서 실제 ODsay 호출을 한 큐로 제어하고 측정한다. 유한한 배치에서는 배치 요청 수를 동시성 상한으로 설정해 상한을 비활성화한 것과 동일하게 실행한다. 장애·지연·다중 사용자 실험은 먼저 모의 upstream으로 수행한다. 운영 설정은 결과 확인 전 변경하지 않는다.

**Tech Stack:** 기존 Node.js 실험 스크립트, Next.js 서버 API, Vitest, JSON/CSV 결과.

**Spec:** 이 대화의 요구 사항과 docs/transit-request-interval-experiment-plan.md. 기존 실험의 선택 규칙과 수치는 새 실험의 결론으로 재사용하지 않는다.

## Global Constraints

- 250ms 또는 500ms를 최적값/안전 한계로 사전 확정하지 않는다.
- 기존 실험의 start 시점은 테스트 클라이언트의 요청 시작이다. 실제 upstream 시작률이나 실제 외부 동시성의 증거로 자동 해석하지 않는다.
- 실제 API 실험 전에 계정 한도, 당일 사용량, 이용 목적의 허용 범위를 확인한다. 모르는 계정 수치를 과거 1,000회로 가정하지 않는다.
- 공식 자료: https://lab.odsay.com/community/boardView?seq=454 및 https://lab.odsay.com/community/noticeView?seq=216 . 제한을 찾기 위해 무제한 호출하지 않는다.
- 타임아웃 30초 고정, 자동 재시도와 오류 감속 비활성화. 실험 사이 30초 이상 휴지, 이미 진행 중인 요청 종료 확인. 이 휴지 시간이 제공자 제한 초기화를 보장한다고 주장하지 않는다.
- 브라우저의 고정 C3/S500 스케줄러를 경유하지 않는다. 운영 서버를 통한 실험은 서버 제한에 가려질 수 있어 전용 로컬 실험 인스턴스를 사용한다.
- 실제 요청 상한 비활성화는 concurrency=해당 실행 총 요청 수로 표현한다. 기존 스크립트에서 concurrency=0은 무제한이 아니라 유효하지 않은 값이다.
- 실험 중 키/사용자 개인정보를 결과와 로그에 저장하지 않는다. 운영 브랜치 설정이나 배포를 변경하지 않는다.

## Review Focus

- 서버 큐가 실험 간격보다 느리게 시작시켜 결과를 왜곡하는지.
- 서로 다른 좌표 조합이나 시간대가 설정 차이로 오해되는지.
- 실패가 빨리 반환되어 완료 시간이 짧아진 것을 개선으로 계산하는지.
- 타임아웃/취소 후 upstream이 종료되지 않았는데 실행 슬롯을 재사용하는지.
- 다중 사용자에게 각각 간격을 적용해 API 키 전체 시작량이 증가하는지.

## Task 2: 실제 API 시작 간격 실험

독립 변수는 시작 간격 S다. C는 비활성화, G=0, 별도 R 제한 비활성화. 한 서버/한 API 키의 하나의 실험 큐에서 실행한다. 현재 API 이용 조건이 이 호출 패턴을 허용하는지 먼저 확인한다. 제한에 막힌 실행을 S 단독 비교라고 표현하지 않는다.

- [ ] 고정 좌표 조합 9개(3x3)를 선정한다. 정상 대중교통 경로를 사용하고 동일/근거리 예외는 별도 검증으로 분리한다. 날짜/출발 시각 조건을 고정한다.
- [ ] 탐색 순서: 500→250→125ms. 각 후보에서 9개 요청의 배치를 1회 수행한다. 단일 요청의 성공으로 판단하지 않으며, 이 1회 결과만으로 운영값을 선택하지 않는다.
- [ ] 각 신규 후보는 직전 통과 후보와 순서를 뒤집어 3x3 배치를 각각 한 번 추가 실행한다. 최초 비교와 합쳐 후보별 최소 2회로 개선 방향을 확인한다. 이는 탐색용이며 최종 확증은 아니다.
- [ ] 다음 후보는 직전 간격의 절반을 정수 ms로 올림한 값으로 제안한다(125→63ms 등). 자동으로 끝없이 진행하지 않는다. 실제 시작량, 호출 예산, 이용 조건, 정상 완료 시간의 개선을 확인하고 확장 여부를 기록한다. 허용 시작률이 있다면 이를 넘는 후보는 실행하지 않는다.
- [ ] 비교한 두 실행 순서 모두에서 더 짧은 후보가 빨랐고 평균 완료 시간이 10% 이상 줄었을 때만 더 짧은 간격으로 확장한다. 10%는 잠정 제품 기준이며 실행 전에 고정한다. 결과가 엇갈리면 추가 반복 또는 보류, 개선이 작으면 구간 세부 비교로 전환한다.
- [ ] 절반씩 줄이는 것은 탐색 효율을 위한 것이며 이분 탐색으로 안전 한계를 확정하는 절차가 아니다. 외부 부하와 제한 방식 때문에 성공/실패가 간격에 대해 항상 일관되지는 않는다.
- [ ] 유망한 구간에서 중간값 1~2개를 추가한다. 예: 250/125ms 구간에서 200/150ms. 제한 오류가 있었던 빠른 후보 쪽으로 즉시 중간값 재시험을 하지 않는다. 별도 실행 시점과 예산을 정한다.
- [ ] 최종 공정 비교 후보는 최대 4개: 500ms 기준선, 유망한 짧은 간격, 필요 시 중간값 1~2개. 후보 제외/선정 이유와 미시험 구간을 기록한다.
- [ ] 공정 비교는 후보별 3x3 배치 4회. 실행 순서를 순환 또는 균형 배치하고, 여러 시간대 블록에서 동일 후보들을 비교한다. 4개면 후보당 36건, 전체 144요청. 순서/날짜/시간대를 결과에 저장한다.
- [ ] 작은 부하에서 개선 정체를 관측해도 5x5나 동시 사용자 부하에서 정체라고 단정하지 않는다. Task 3에서 최근 더 짧은 후보의 효과도 확인한다.
- [ ] 평균 배치 완료 시간, 개별 실행값/범위, 정상 결과 수, 오류 분류, 실제 최대 C와 초당 시작량, 슬롯 제한 대기 시간을 산출한다. 4회 반복으로 배치 p95를 신뢰성 있게 추정했다고 표현하지 않는다.
- [ ] 예산 산식: 탐색/추가 비교 실행 횟수를 E, 최종 후보 수를 K라 하면 Task 2는 9E+36K요청. 다음 배치 시작 전에 이미 진행한 호출, 다음 배치 전체, 최종 검증용 172요청과 예비량이 예산에 들어오는지 확인한다. 예산 부족은 미검증 종료 사유이며 최적값 발견으로 해석하지 않는다.

## Task 3: 실제 API 최종 후보 확인

- [ ] 상한 없는 500ms 기준선과 공정 비교에서 유망한 짧은 간격 두 후보를 선택한다. 개선 정체가 탐색 종료 이유였다면 가장 짧게 통과한 후보를 큰 부하에서 확인한다. 500ms 비교도 C 비활성화이므로 현재 운영 C3/S500과 구분한다.
- [ ] 후보별 5x5 두 번을 교차 실행한다: 총 100요청.
- [ ] 후보별 두 세션의 3x3을 동시에 제출하되 하나의 글로벌 큐에 넣는다. 두 번 반복: 총 72요청. 사용자별 완료 시간과 공정성도 기록한다.
- [ ] 기본 Task 3는 172요청. 전체 예상량은 9E+36K+172이며 사전 정상 경로 확인, 추가 후보 검증, 운영 기준선 비교, 이미 시작한 요청을 별도 합산한다. 예: E=7, K=4이면 379요청. 현재 계정 예산으로 실행 범위를 확정하고, 날짜를 나누면 후보와 날짜 효과가 겹치지 않게 균형 배분한다.
- [ ] 이전 C3/S500 운영 기준선도 별도 3x3 세 번 측정 가능(+27요청). 이는 두 변수가 달라지는 제품 전체 비교이며 S 단독 효과로 해석하지 않는다.

## Task 4: 동시 상한 필요성은 모의 장애로 검증

고정: Task 2에서 유망한 S. 변수: C=상한 없음, 3, 5, 8. 이 숫자는 실험 후보이지 운영 정답이 아니다.

- [ ] 정상 0.5초/2초, 일부 10초, 전체 30초 무응답, 일부 429, 5xx를 각각 재현한다.
- [ ] 배치 9/25/64요청, 세션 1/2/5개를 비교한다. 로컬 모의 환경이므로 실제 API 쿼터를 소비하지 않는다.
- [ ] 2초 후 취소/재계산 시 이미 외부로 나간 요청, 남은 큐, 종료 시간, 낡은 결과 혼입 여부를 확인한다.
- [ ] 프로세스 메모리, 진행 요청 최고치, 큐 대기, 배치 완료 시간, 세션별 완료 시간과 성공률을 측정한다.
- [ ] 병목이나 비용 차이가 없으면 C 추가 실제 API 비교를 생략한다. 보호 효과가 관측되면 상한 없음과 후보 상한 한 개를 실제 정상 부하에서 대조해 속도 비용을 확인한다(별도 예산 산정).
- [ ] 다중 인스턴스 운영에서는 로컬 큐를 키 전체 제한이라고 표현하지 않는다. 분산/global 제어 여부는 별도 설계 항목이다.

## Task 5: 선택과 보고

- [ ] 전체 후보별 요청 수와 실패 수를 함께 보고한다. 오류 0회는 장기 안정성 보장이 아니다.
- [ ] 429/ODsay -1 감지 시 새 요청의 시작을 즉시 중단하고 더 짧은 간격으로 진행하지 않는다. 이미 시작한 호출도 결과/예산에 포함한다. 느린 후보 재개도 냉각 대기만으로 안전하다고 가정하지 말고 별도 시점과 조건을 기록한다.
- [ ] 경로 없음 등 입력 관련 오류는 해당 조합을 확인한다. 경로 변경이 필요하면 영향받는 후보 모두를 동일한 새 조합으로 재시험하며 실패 기록을 삭제하지 않는다. 타임아웃/5xx/네트워크 오류는 해당 후보 판단을 보류하고 외부 장애와 설정 영향을 구분한다. 연속 3회면 실험 전체를 중단한다.
- [ ] 예산 초과, 중복 호출, 시간 기록 누락은 중단한다. 이미 시작한 호출까지 예산에 포함한다.
- [ ] 선택 규칙: 정상 결과 완성도를 충족하는 후보끼리 동일 부하와 반복 블록에서 비교한다. 더 짧은 간격의 개선이 정상 배치 평균 10% 미만이면 비교한 두 후보 중 더 긴 간격을 우선하는 잠정 정책을 사용한다. 이는 무조건 운영 500ms로 복귀하는 규칙이 아니다. 10%는 API 특성이 아니라 사전에 정한 제품 기준이다.
- [ ] 종료 사유를 구분한다: 속도 개선 정체, 제한 응답, 예산/이용 조건 한계, 결과 불일치. 150ms 같은 특정 간격에 도달했다는 이유만으로 종료하지 않는다. 오류 경계를 반드시 발견하는 것을 목표로 삼지 않는다.
- [ ] 시간대/반복별 결과가 엇갈리거나 최악 완료 시간이 크게 나빠지면 결론을 유보하고 추가 반복을 설계한다.
- [ ] C는 정상 성능의 변화와 모의 지연/취소에서의 보호 효과를 함께 보고 결정한다. 무조건 상한을 둘 필요도, 무조건 무제한이 최적이라는 결론도 사전 설정하지 않는다.
- [ ] 도보 -98 시간 0, 첫 번째 경로 선택, 실패 후보 점수 제외 등 추천 정확성은 별도 계약 테스트로 확인한다. 스케줄링 실험은 경로 정확성을 입증하지 않는다.
- [ ] 산출물: docs/results/에 run 설정과 JSON/CSV, 새 결과 요약 문서에 후보 선택/미검증 범위/예산/운영 제한을 기록한다.

## 2026-10-26 후속 반복 비교 계획 (사용자 요청 시 실행)

기존 계획에 따른 실험은 10/26의 250/500ms 단일 세션 비교로 완료했다. 아래 5일은 결론을 절대적으로 확정하기 위한 필수 단계가 아니라, 날짜별 변동을 더 확인하는 선택적 후속 검증이다. 사용자가 추가 실험 실행을 요청한 날에 해당 날짜 한 배치만 실행하며 자동 예약하지 않는다.

| 1일차 | 250ms 3×3 → 500ms 3×3 | 각 간격의 균형 잡힌 6개 경로 부분 반복 |
| 2일차 | 500ms 3×3 → 250ms 3×3 | 각 간격의 다음 6개 경로 부분 반복 |

매일 동일한 9개 기준 경로, 동시 상한 없음, 같은 타임아웃과 최소 30초 배치 휴지를 사용한다. 완성 배치 순서는 날짜별로 교차한다. 추가 6개 표본은 전체 9개 경로를 날짜에 걸쳐 균형 있게 돌려 관측하고, 3×3 완성 배치의 완료 시간이나 반복수와 합치지 않는다. 한 날 최대 30회 시도 예산 안에 실패·진행 중 호출도 포함한다. 오류가 나면 해당 배치의 새 요청을 즉시 중단하고 기존 회복 규칙을 적용한다. 날짜·시간대·순서·오류 분류·요청별 지연을 기록한다.

5일 뒤에는 후보별 관측 성공률, 완성 배치 완료 시간과 변동 범위를 비교한다. 결과가 일관되면 “이 시험 조건에서 250ms가 더 빠르고 성공률이 비슷하게 관측됐다”처럼 범위를 한정해 결론을 갱신한다. 5일 결과만으로 장기 안정성이나 다른 계정·부하에서의 보장을 주장하지 않는다. 오류율 1% 미만을 95% 신뢰수준으로 뒷받침하려면 독립 시행 가정 아래 후보별 약 300회 무오류 관측이 필요하다는 대략적 기준을 참고하되, 일별 요청 간 상관 때문에 이를 통계적 보증으로 사용하지 않는다.
## 2026-10-26 실험 결과 반영

사용자 결정으로 `useTransitMatrix`의 최소 요청 시작 간격과 서버 `TRANSIT_SERVER_MIN_START_GAP_MS` 기본값을 250ms로 적용한다. `.env.example`도 250ms로 맞춘다. 기존 서버 동시 실행 상한 C3는 유지한다. 최근 1초 시작 상한은 이후 R2에서 R4로 올렸다. R2로는 250ms 간격에서도 1초에 두 번만 시작돼 시작 속도가 500ms와 같아지고, 재실험에서 1초 4회 시작(250ms)은 모두 정상, 5회 이상(200ms·125ms)에서 본문 429가 나왔기 때문이다. 서버 배포 환경에 변수가 500ms로 명시되어 있으면 그 설정은 별도 변경이 필요하며, 이 PR은 배포 환경을 수정하지 않는다. 5일 추가 비교는 자동 예약하지 않고 사용자 요청 시 해당일 계획분을 진행한다.

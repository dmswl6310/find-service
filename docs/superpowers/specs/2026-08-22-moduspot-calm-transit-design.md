# 모두스팟 Calm Transit 디자인 명세

- 날짜: 2026-08-22
- 상태: 대화에서 방향 승인 완료, 문서 검토 대기
- 적용 대상: 모두스팟 홈 비교 경험과 이를 지탱하는 디자인 시스템
- 구현 상태: 미구현

## 1. 요약

모두스팟은 사용자가 이미 정한 여러 출발지와 여러 목적지 후보를 대중교통 이동시간으로 비교하는 서비스다. 이번 개편은 새로운 장소 추천 기능을 추가하지 않는다. 현재의 핵심 계산인 `최장 이동시간 + 평균 이동시간`을 유지하면서, 사용자가 가장 균형 잡힌 후보와 그 근거를 더 빠르게 이해하도록 화면 구조와 디자인 시스템을 다시 설계한다.

선택된 방향은 `Calm Transit`이며, 레이아웃은 `Map-first Workspace`다. 제품의 인상은 신뢰할 수 있는 교통 비교 도구 70%, 소모임에 어울리는 친근함 30%로 맞춘다. 지도와 비교 결과가 시선을 주도하며, 친근함은 장식이 아니라 쉬운 문구와 부담 없는 상호작용으로 표현한다.

## 2. 현재 상태에서 해결할 문제

현재 UI에는 출발지와 목적지를 색으로 구분하고, 지도와 결과표를 함께 제공하는 좋은 기반이 있다. 다만 다음 문제가 체계적인 확장을 막는다.

- 첫 화면의 큰 제목, 설명, 단계 안내, 많은 내비게이션 링크가 핵심 입력 행동과 경쟁한다.
- 모바일 헤더가 여러 줄로 커지고, 핵심 CTA가 첫 화면에서 멀어진다.
- Tailwind 팔레트 색과 16진수 색상이 여러 컴포넌트에 직접 들어가 있다.
- 정의되지 않은 의미 기반 클래스가 일부 사용되어 스타일 계약이 불완전하다.
- `MainContent`, `ResultTable`, `MiniMap`처럼 상태 조립, 계산 결과 해석, 표현이 한 파일에 섞인 영역이 있다.
- 레이아웃에서 Inter를 선언하지만 전역 CSS의 폰트 변수 연결이 일치하지 않아 실제 글꼴이 의도와 다를 수 있다.
- 왕관 이모지, 그라데이션 배지, 많은 둥근 카드가 기능보다 장식을 앞세워 AI가 자동 생성한 화면처럼 느껴질 수 있다.

## 3. 제품 범위

### 포함

- 사용자가 입력한 출발지와 목적지 후보의 비교
- 평균 이동시간과 최장 이동시간의 동시 표현
- 기존 황금 밸런스 계산 결과의 시각적 우선순위 개선
- 지도, 후보 순위, 상세 경로 사이의 명확한 연결
- 모바일 390px과 데스크톱 1440px의 반응형 구조
- 의미 기반 디자인 토큰과 공통 컴포넌트
- 개발 전용 Design Lab
- 기능 회귀, 접근성, 시각 회귀 검증

### 제외

- 출발지만 입력하면 새로운 모임 장소를 찾아주는 추천 기능
- 음식점, 카페, 업체 예약, 쿠폰, 광고 또는 제휴 기능
- 황금 밸런스 계산식 변경
- 대중교통 API 또는 요청 스케줄러의 동작 변경
- 다크 테마 출시
- Production 사용자가 선택하는 테마 전환 기능
- 이번 작업과 무관한 콘텐츠 또는 백엔드 리팩터링

추천 기능을 나중에 추가할 수 있도록 컴포넌트 경계는 열어 두되, 이번 명세에 추천 데이터 소스나 제휴 모델은 포함하지 않는다.

## 4. 유지할 도메인 규칙

`utils/fairness.ts`의 현재 규칙을 유지한다.

1. 각 목적지 후보에 대해 정상 결과의 이동시간을 모은다.
2. 후보의 `max`와 `avg`를 계산한다.
3. `score = max + avg`로 점수를 계산한다.
4. 모든 출발지의 정상 경로가 존재하는 후보만 황금 밸런스 대상이 된다.
5. 가장 낮은 점수의 후보를 황금 밸런스로 선택한다.

경로 비교 자체는 출발지 1곳과 후보지 1곳부터 가능하다. `황금 밸런스`는 현재 로직과 동일하게 출발지 2곳 이상, 후보지 2곳 이상일 때만 나타난다. 디자인 개편은 새로운 장소 개수 제한을 도입하지 않는다.

## 5. 검토한 디자인 방향

| 방향 | 성격 | 장점 | 단점 | 구현 비용 | 결정 |
| --- | --- | --- | --- | --- | --- |
| Calm Transit | 절제된 교통 도구 | 지도와 수치의 신뢰도가 높고 확장하기 쉽다 | 지나치게 절제하면 개성이 약할 수 있다 | 중 | 선택 |
| Friendly Meetup | 따뜻한 소모임 서비스 | 처음 쓰는 사람이 편하고 친근하다 | 데이터 비교의 신뢰감이 약해질 수 있다 | 중 | 문구의 친근함만 참고 |
| Urban Data | 고밀도 분석 도구 | 많은 수치를 한 화면에서 비교하기 좋다 | 일상적인 모임에는 차갑고 복잡하다 | 상 | 제외 |

세 방향을 한 화면에서 혼합하지 않는다. Calm Transit의 색, 간격, 표면, 타이포그래피를 일관되게 사용하며 Friendly Meetup의 영향은 쉬운 한국어 문구에만 제한한다.

## 6. 정보 구조

### 6.1 데스크톱 1440px

화면은 압축된 전역 헤더와 고정형 비교 작업공간으로 나눈다.

- 헤더: 브랜드, 현재 기능, 이용 방법, 서비스 소개만 우선 노출한다.
- 왼쪽 패널: 약 360px 너비로 출발지와 후보지 입력 또는 비교 결과를 표시한다.
- 지도: 남은 너비를 모두 사용하고 사용자가 선택한 장소와 경로를 지속적으로 보여준다.
- 지도 결과 요약: 결과 상태에서 지도 하단에 선택 후보의 평균, 최장, 상세 경로 행동을 표시한다.
- 상세 매트릭스: 기본 화면을 덮지 않고 사용자가 요청할 때 패널이나 시트로 연다.

입력에서 결과로 이동해도 지도를 교체하지 않는다. 왼쪽 패널의 내용만 입력 패널에서 결과 패널로 전환해 공간적 맥락을 보존한다.

### 6.2 모바일 390px

- 상단 앱바는 한 줄로 유지한다.
- 지도는 화면 배경의 주요 영역을 차지한다.
- 입력, 계산, 결과는 지도 위 바텀시트에서 상태에 따라 전환한다.
- 바텀시트는 현재 후보와 핵심 지표를 먼저 보여주고, 상세 내용은 확장하거나 별도 시트로 연다.
- CTA는 현재 시트 안에서 쉽게 닿는 위치에 둔다.
- 데스크톱 매트릭스를 그대로 축소하지 않고 후보별 카드 또는 행 목록으로 바꾼다.

## 7. 화면 상태

### 7.1 빈 상태

- 왼쪽 패널 또는 모바일 바텀시트에 서비스의 핵심 설명을 짧게 표시한다.
- 출발지와 후보지 검색을 모두 노출한다.
- 지도는 장소가 추가될 위치임을 설명하는 차분한 빈 상태를 표시한다.
- 조건이 충족되지 않은 CTA는 비활성 이유를 문구로 설명한다.
- 출발지와 후보지는 색뿐 아니라 원형과 사각형으로 구분한다.

### 7.2 입력 상태

- 추가된 장소를 번호 또는 문자, 장소명, 주소, 제거 행동으로 표시한다.
- 출발지는 `1, 2, 3`, 후보지는 `A, B, C`로 지도와 목록을 연결한다.
- 장소 행을 선택하면 지도에서 해당 마커가 강조된다.
- CTA는 계산할 셀의 수를 `9개 경로 비교하기`처럼 명확하게 알린다.
- 장소 추가 및 제거는 입력 그룹 안에서 처리하고 별도의 장식 카드를 추가하지 않는다.

### 7.3 계산 중 상태

- 입력과 지도 맥락을 유지한다.
- `6 / 9`처럼 완료된 경로 수를 표시한다.
- 완료된 결과는 유지하고 다음 계산 대상을 알린다.
- 전체 화면을 불투명한 스피너로 막지 않는다.
- 모션 감소 환경에서는 회전 애니메이션 없이 정적 진행 표시를 사용한다.

### 7.4 비교 결과 상태

- 왼쪽 패널의 첫 정보는 황금 밸런스 후보, 평균 이동시간, 최장 이동시간이다.
- `황금 밸런스`라는 이름은 유지한다.
- 왕관 이모지와 그라데이션은 제거하고, 제한된 balance 색과 왼쪽 강조선으로 표현한다.
- 후보 순위는 평균과 최장을 함께 표시한다.
- 지도 하단 요약은 현재 선택한 후보와 경로를 반영한다.
- 전체 매트릭스와 상세 경로는 사용자의 명시적인 행동으로 연다.
- `입력 수정`은 결과를 버리지 않고 입력 패널로 돌아가는 낮은 강조 행동이다.

### 7.5 부분 실패와 전체 실패

- 일부 경로가 실패해도 성공한 셀과 후보 결과는 유지한다.
- 실패 셀은 `경로 없음` 또는 구체적인 실패 사유를 표시한다.
- 출발지 중 하나라도 정상 결과가 없는 후보는 황금 밸런스에서 제외하고 이유를 표시한다.
- 전체 실패 시 입력을 유지하고 다시 계산할 수 있게 한다.
- 지도 경로 그래픽만 실패한 경우 평균, 최장, 순위, 텍스트 경로는 계속 사용할 수 있어야 한다.

## 8. 시각 언어

### 8.1 색

색은 행동이나 도메인 의미가 있을 때만 사용한다.

- 진한 청록: 주요 행동과 선택
- 청록빛 파랑: 출발지
- 차분한 적갈색: 목적지 후보
- 저채도 황토색: 황금 밸런스
- 중립적인 회백색: 캔버스, 지도 주변 표면, 구분선

출발지, 후보지, 황금 밸런스의 색은 서로 바꿔 쓰지 않는다. 황금 밸런스 색은 추천 결과에만 사용하며 일반 경고색으로 사용하지 않는다.

### 8.2 타이포그래피

- 기본 글꼴: self-hosted Pretendard Variable
- 사용 굵기: 400, 500, 600
- Display: 데스크톱 32/40, 모바일 24/32
- Section title: 20/28
- Body: 16/24
- Compact body: 14/20
- Label: 12/16
- 수치: tabular numerals 사용

700 이상의 굵기를 일반 UI에 사용하지 않는다. 제목 크기와 굵기보다 간격과 위치로 계층을 만든다.

### 8.3 표면과 장식

- 중첩 카드를 피한다.
- 그림자는 지도 위 시트, 모달, 팝오버 등 실제로 떠 있는 표면에만 사용한다.
- 기본 모서리 반경은 8px이며 큰 시트는 12px까지 사용한다.
- 장식 목적의 그라데이션과 이모지를 사용하지 않는다.
- 한 영역에 높은 강조 CTA는 하나만 둔다.

정확한 토큰 값과 사용 규칙은 `docs/design-system.md`를 기준으로 한다.

## 9. 컴포넌트 구조

### 9.1 일반 UI

- `Button`: 강조도, 크기, 로딩, 비활성 상태
- `IconButton`: 명확한 접근성 이름이 있는 보조 행동
- `SearchField`: 검색, 로딩, 오류, 결과 팝오버
- `Badge`: 짧은 상태 라벨. 황금 밸런스의 주 표현으로 남용하지 않는다.
- `Progress`: 결정형 진행률과 접근성 속성
- `InlineNotice`: 정보, 경고, 오류
- `BottomSheet`: 모바일 입력, 결과, 상세 경로 표면

### 9.2 장소 도메인 UI

- `LocationGroup`: 출발지 또는 후보지 그룹의 제목, 개수, 추가 행동
- `LocationSearch`: 장소 검색과 결과 선택
- `PlaceRow`: 장소 식별자, 이름, 주소, 제거, 선택 상태
- `MapMarker`: 출발지 원형과 후보지 사각형의 일관된 표현

### 9.3 결과 도메인 UI

- `BalanceSummary`: 황금 밸런스 이름, 근거, 평균, 최장
- `CandidateRankList`: 후보 순위와 두 핵심 지표
- `RouteMatrix`: 데스크톱 다대다 상세 비교
- `RouteDetailSheet`: 모바일과 데스크톱의 상세 경로 표면
- `CalculationProgress`: 진행 셀, 전체 셀, 현재 후보
- `PartialFailureNotice`: 실패 요약과 상세 접근

### 9.4 화면 조립

- `ComparisonWorkspace`: 입력, 계산, 결과 상태와 전체 레이아웃을 조율
- `LocationPanel`: 출발지와 후보지 입력
- `ResultPanel`: 황금 밸런스와 후보 순위
- `MapWorkspace`: 지도, 마커, 선택 경로, 지도 위 요약

`ComparisonWorkspace`만 앱 상태와 훅을 조율한다. 하위 표현 컴포넌트는 가능한 한 데이터와 콜백을 props로 받고, 황금 밸런스 계산이나 API 호출을 내부에서 수행하지 않는다.

## 10. 데이터 흐름과 기존 코드 경계

1. `store/useAppStore.ts`가 출발지, 후보지, 비교 결과의 앱 상태를 유지한다.
2. `hooks/useLocationSearch.ts`가 검색 상태를 제공한다.
3. `hooks/useTransitMatrix.ts`가 현재 요청 스케줄과 부분 성공 결과를 제공한다.
4. `utils/fairness.ts`가 황금 밸런스 후보 ID를 계산한다.
5. 화면 조립 계층이 이 데이터를 표현용 모델로 변환한다.
6. `LocationPanel`, `ResultPanel`, `MapWorkspace`가 동일한 모델을 받아 동기화한다.
7. 결과 행 또는 지도 마커 선택은 현재 선택 경로 ID 하나를 통해 양쪽에 반영된다.

이번 작업은 `useTransitMatrix`의 동시성 또는 요청 간격을 변경하지 않는다. `MainContent`와 `ResultTable`을 분리할 때도 현재 테스트가 보장하는 공유 URL 복원, 자동 계산, 부분 실패 보존, 지도 선택 동기화를 유지한다.

## 11. 오류 처리

- 검색 실패: 입력값을 유지하고 검색창 아래에서 재시도를 안내한다.
- 결과 없음: 오류가 아니라 검색 결과 없음 상태로 구분한다.
- 일부 경로 실패: 성공 결과를 유지하고 실패 셀만 표시한다.
- 후보 불완전: 황금 밸런스 대상에서 제외하고 이유를 표시한다.
- 전체 경로 실패: 입력을 유지하고 다시 계산 행동을 제공한다.
- 지도 그래픽 실패: 텍스트 결과와 상세 지표는 유지한다.
- 오류 표현: 색, 아이콘, 제목, 설명을 함께 사용한다.
- 접근성: 상태 변경은 `aria-live` 또는 적절한 alert/status 역할로 전달한다.

## 12. 개발 전용 Design Lab

`/design-lab`은 실제 Production 화면과 동일한 컴포넌트를 고정 데이터로 검토하는 개발 전용 경로다.

- Production 환경에서는 `notFound`로 응답한다.
- 외부 지도, 장소 검색, 대중교통 API를 호출하지 않는다.
- 토큰, 타이포그래피, 버튼, 검색창, 알림, 진행률을 개별 확인한다.
- 장소 그룹, 마커, 황금 밸런스, 후보 순위, 매트릭스, 상세 시트를 확인한다.
- 빈 상태, 입력 완료, 계산 중, 성공, 부분 실패, 전체 실패 시나리오를 제공한다.
- 390px, 768px, 1440px 기준을 확인한다.
- 시나리오는 URL 또는 안정적인 컨트롤로 재현 가능해야 한다.
- 동일한 시나리오를 Playwright 시각 회귀 테스트가 사용한다.

Design Lab은 Storybook을 새로 도입하지 않고 현재 Next.js 앱과 테스트 인프라를 재사용한다.

## 13. 페이지 적용 순서

1. 현재 기능 및 E2E 테스트를 기준선으로 고정한다.
2. 폰트와 의미 기반 토큰을 추가한다.
3. 일반 UI 컴포넌트와 Design Lab의 foundation 시나리오를 만든다.
4. 장소 도메인 컴포넌트와 입력 시나리오를 만든다.
5. 홈의 빈 상태와 입력 상태를 새 컴포넌트로 교체한다.
6. 데스크톱 Map-first 셸과 모바일 바텀시트를 적용한다.
7. 계산 진행 상태를 적용한다.
8. 황금 밸런스, 후보 순위, 상세 매트릭스를 적용한다.
9. 지도 선택 동기화와 상세 경로 모달을 새 표면에 연결한다.
10. 헤더와 모바일 내비게이션을 정리한다.
11. 소개, 이용 방법, 팁, 정책 등 보조 페이지에 토큰을 적용한다.
12. 남은 직접 팔레트 색과 사용하지 않는 스타일을 제거한다.

각 단계는 독립적으로 검증하고, 다음 단계가 이전 단계의 실패를 숨기지 않도록 한다.

## 14. 검증 전략

### 14.1 단위 및 컴포넌트 검증

- 기존 `utils/fairness.ts` 규칙을 테스트로 고정한다.
- 후보 순위용 표현 모델이 평균과 최장을 올바르게 계산하는지 검증한다.
- 빈 상태, 입력, 계산, 성공, 부분 실패의 조건부 렌더링을 검증한다.
- 의미 기반 variant가 올바른 토큰을 사용하는지 검증한다.

### 14.2 E2E 기능 회귀

기존 Playwright 회귀 테스트를 유지하고 새 UI의 접근성 이름을 기준으로 갱신한다.

- 공유 URL 복원과 자동 계산
- 안정적인 요청 스케줄
- 한국어 장소 공유 URL
- 결과 선택과 지도 경로 동기화
- 장소 제거 및 추가 후 결과 정리
- 부분 실패에서 성공 셀 보존
- 모바일 바텀시트의 입력과 결과 흐름

### 14.3 시각 회귀

- Playwright `toHaveScreenshot`을 사용한다.
- Design Lab 고정 시나리오를 390px과 1440px에서 캡처한다.
- 대상 상태는 빈 상태, 입력 완료, 계산 중, 비교 결과, 부분 실패다.
- 외부 카카오 지도 타일은 픽셀 기준선에서 제외하고 고정 지도 표면을 사용한다.
- 애니메이션과 시간 의존 값을 비활성화한다.
- 폰트가 로드된 뒤 캡처한다.
- 의도한 시각 변경만 기준 스크린숏 갱신 사유로 인정한다.

### 14.4 접근성 및 수동 검토

- 키보드만으로 검색, 장소 추가, 제거, 결과 선택, 상세 경로 열기가 가능해야 한다.
- 포커스 표시를 제거하지 않는다.
- 주요 텍스트는 WCAG AA 4.5:1 이상을 목표로 한다.
- 터치 대상은 최소 44px을 목표로 한다.
- 색만으로 출발지, 후보지, 실패, 선택 상태를 구분하지 않는다.
- 320px에서 가로 스크롤이나 잘림이 없어야 한다.
- 390px과 1440px에서 핵심 CTA와 결과 요약이 첫 사용 흐름 안에 보여야 한다.

각 적용 단계의 기본 검증 순서는 `lint → unit → e2e → screenshot`이다.

## 15. 성공 기준

- 첫 화면에서 출발지와 후보지 입력 행동을 즉시 찾을 수 있다.
- 데스크톱에서 지도와 입력 또는 결과가 한 화면 안에 유지된다.
- 모바일에서 헤더가 한 줄이며 핵심 CTA가 긴 설명 아래로 밀리지 않는다.
- 황금 밸런스 후보와 평균, 최장 이동시간을 결과 진입 즉시 이해할 수 있다.
- 부분 실패가 전체 성공 결과를 숨기지 않는다.
- Production 컴포넌트에서 Tailwind 팔레트 색을 직접 사용하지 않는다.
- 출발지, 후보지, 황금 밸런스의 의미가 목록, 지도, 결과에서 일관된다.
- Design Lab과 시각 회귀 테스트가 모든 핵심 상태를 재현한다.
- 기존 공유 URL, 요청 스케줄, 부분 성공, 지도 선택 동기화 테스트가 계속 통과한다.

## 16. 위험과 대응

### 지도와 결과를 동시에 크게 보여주려는 욕심

모든 정보를 기본 화면에 펼치면 Urban Data 방향으로 변질된다. 기본 결과는 황금 밸런스와 후보 순위까지만 보여주고 전체 매트릭스는 요청 시 연다.

### 컴포넌트 분해 중 동작 회귀

표현 컴포넌트 분리 전에 현재 E2E를 기준선으로 유지한다. 계산 훅과 fairness 유틸은 디자인 변경과 분리한다.

### 외부 지도 때문에 불안정한 스크린숏

시각 회귀는 Design Lab의 고정 지도 표면을 사용하고 실제 지도는 기능 및 수동 검토 대상으로 둔다.

### 문서와 구현의 불일치

설계 결정은 이 명세에 남기고 실제 토큰 및 컴포넌트 계약은 `docs/design-system.md`에서 유지한다. 새 토큰이나 공통 컴포넌트를 추가할 때 Design Lab과 문서를 함께 갱신한다.

## 17. 승인 이후 절차

1. 사용자가 이 문서를 검토하고 변경 여부를 결정한다.
2. 승인 후 Superpowers `writing-plans`로 구현 계획을 작성한다.
3. 구현은 격리된 작업공간과 테스트 우선 흐름으로 진행한다.
4. Production 코드 변경은 구현 계획 승인 전 시작하지 않는다.

현재 명세에 미결정 항목은 없다.

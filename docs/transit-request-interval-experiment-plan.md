# ODsay 요청 스케줄링 실험 계획 v2

## 1. 이 계획이 답해야 하는 질문

이 실험의 목표는 단순히 `250ms`를 다른 숫자로 교체하는 것이 아니다. 다대다 경로 계산에서 **다음 요청을 어떤 조건과 시점에 시작해야 안정성과 속도를 함께 만족하는지** 결정하는 것이다.

최종적으로 아래 형태의 운영 규칙을 도출한다.

```text
다음 요청 시작 가능 =
  현재 실행 중인 요청 수 < 동시성 상한
  AND 직전 요청 시작 후 최소 간격 경과
  AND 최근 시간 창의 요청 시작 한도 미초과
  AND 오류 후 냉각 상태가 아님
```

실험이 끝나면 다음 값을 근거와 함께 결정해야 한다.

- 최대 동시 요청 수 `C`
- 최소 요청 시작 간격 `S`
- 응답 완료 후 추가 대기시간 `G`
- 최근 1초 또는 10초의 요청 시작 상한 `R`
- 429 또는 제한 의심 오류 발생 시 냉각시간 `B`
- 재시도 여부와 최대 횟수
- 사용자별 제한인지 서비스 전체 제한인지
- 허용할 최대 행렬 크기

## 2. 이전 계획에서 잘못 좁힌 범위

이전 실험은 완전 순차 실행, 즉 `C=1`인 상태에서 응답 완료 후 추가로 `250ms`를 쉬어야 하는지만 확인했다.

확인된 사실:

- `C=1`, `G=0ms`로 8 × 8까지 제한 오류 없이 완료됐다.
- 순차 실행에서 `G=250ms`를 제거하면 완료시간이 단축됐다.

확인하지 못한 사실:

- `C=2`, `3`, `4` 중 어디까지 안전한가?
- 요청 시작 간격 `S`가 몇 ms여야 하는가?
- 빠른 응답이 연속될 때 초당 시작 요청 수가 높아져도 안전한가?
- 느린 요청과 빠른 요청이 섞이면 어떤 스케줄링 방식이 안정적인가?
- 여러 사용자가 동시에 계산하면 공유 API 키 기준으로 몇 요청이 겹치는가?
- 클라이언트별 순차 실행만으로 서비스 전체를 보호할 수 있는가?

따라서 이전 결과만으로 `C=1`이 최적이라고 결론 내리거나 `0ms`를 최종 운영값으로 확정하지 않는다.

## 3. 공식 정책으로 확인된 제약

ODsay 공식 개발자 포럼 답변에 따르면 서버 과부하 및 API 악용 방지를 위해 **서비스 유형별 초당 호출 건수를 제한**하지만 정확한 수치는 공개하지 않는다.

- [ODsay 공식 답변: 서비스 유형별 초당 API 호출 제한](https://lab.odsay.com/community/boardView?seq=454)
- [ODsay 정책 공지: 기본 용도는 출발-도착 경로검색 단일 호출](https://lab.odsay.com/community/noticeView?seq=216)
- [ODsay API 일일 호출 정책 안내](https://lab.odsay.com/community/noticeView?seq=2)

이 때문에 실제 API에 무제한으로 요청을 보내 임계점을 역산하는 방식은 사용하지 않는다.

실제 API 실험 전 필수 조건:

1. 현재 계정의 서비스 등급과 일일 호출 한도를 확인한다.
2. 당일 이미 사용한 호출량을 확인한다.
3. 실험용 일일 예산을 정한다.
4. 대량·반복 호출이 현재 이용 목적과 정책에 맞는지 확인한다.
5. 필요하면 ODsay에 다대다 경로 비교 서비스의 허용 호출 패턴을 문의한다.

2026-07-28에는 통제 실험에서 유효 요청 562건을 이미 사용했다. 계정 한도와 다음 초기화 시점을 확인하기 전에는 추가 실제 부하 실험을 진행하지 않는다.

## 4. 스케줄링 변수를 정확히 구분한다

### 4.1 최대 동시 요청 수 `C`

동시에 응답을 기다릴 수 있는 요청 수다.

```text
C=1: A 완료 후 B 시작
C=2: A와 B 실행 중, 둘 중 하나가 끝나면 C 시작 가능
C=3: 최대 세 요청이 겹침
```

### 4.2 최소 요청 시작 간격 `S`

이전 요청이 끝났는지와 별개로 두 요청의 **시작 시각** 사이에 확보할 최소 간격이다.

```text
S=500ms:
00.000 A 시작
00.500 이후 B 시작 가능
01.000 이후 C 시작 가능
```

`C=2, S=500ms`라면 요청은 최대 두 개까지 겹칠 수 있지만 초당 시작량은 대략 2개 이하로 제한된다.

### 4.3 응답 완료 후 추가 대기시간 `G`

빈 동시성 슬롯이 생겨도 완료 직후 바로 새 요청을 넣지 않고 쉬는 시간이다.

```text
A 완료 → G만큼 대기 → 다음 요청 허용
```

`C=1`에서는 의미가 명확하지만, `C>1`에서는 다른 요청이 실행 중일 수 있으므로 `S` 및 시간 창 제한과 함께 정의해야 한다.

### 4.4 시간 창 요청 상한 `R`

최근 1초 또는 10초 안에 시작할 수 있는 요청 수다.

예:

```text
R=2/1s: 최근 1초 동안 시작 요청은 최대 2개
```

응답이 평소보다 매우 빠르게 끝나더라도 갑작스러운 요청 폭주를 막는다.

### 4.5 오류 냉각시간 `B`

429 또는 제한 의심 오류가 발생했을 때 새로운 요청을 받지 않는 시간이다.

이 값은 정상 호출 간격과 분리한다. 정상 상태를 불필요하게 느리게 만들지 않고, 제한 신호가 있을 때만 보수적으로 동작하기 위함이다.

## 5. 비교할 스케줄러 유형

### P0. 현재 운영 기준선

```text
C=1
S=제한 없음
G=250ms
R=없음
```

### P1. 순차 즉시 실행

```text
C=1
S=제한 없음
G=0ms
R=없음
```

이전 실험에서만 검증된 방식이다.

### P2. 제한된 동시성 + 최소 시작 간격

```text
C=2 또는 3
S=1000/750/500/250ms
G=0ms
```

실제 운영 후보를 찾는 핵심 실험군이다.

### P3. 제한된 동시성 + 시간 창 상한

```text
C=2 또는 3
R=1/1s, 2/1s, 3/1s
G=0ms
```

응답시간이 갑자기 짧아질 때도 호출률을 일정하게 유지하는지 확인한다.

### P4. 혼합형

```text
C=2
S=후보값
R=후보값/1s
G=0ms
```

동시성과 초당 시작량을 모두 제한한다. 최종 운영 후보로 가장 유력한 구조다.

### P5. 적응형

정상 상태에서는 P4로 실행하고 제한 신호가 발생하면:

1. 새 요청 시작 즉시 중단
2. 진행 중 요청은 완료 대기
3. 냉각시간 적용
4. 다음 계산부터 `C=1` 및 더 긴 `S`로 강등
5. 반복 제한 오류 시 자동 재시도하지 않고 사용자에게 부분 실패 표시

적응형은 제한을 탐색하기 위한 수단이 아니라 운영 중 예외를 안전하게 처리하기 위한 수단이다.

## 6. 실험 환경을 세 층으로 분리한다

### 6.1 계층 A: 가상 ODsay

실제 API를 호출하지 않는다. 응답시간과 오류를 통제할 수 있는 mock upstream으로 스케줄러 자체를 검증한다.

응답시간 분포:

- 고정 100ms
- 고정 500ms
- 고정 1000ms
- 100~1500ms 무작위
- 90%는 300ms, 10%는 3000ms
- 처음 10개는 느리고 이후 매우 빠른 응답
- 처음 10개는 빠르고 이후 느린 응답

오류 주입:

- HTTP 429
- ODsay `-1`
- HTTP 500/502/503
- 타임아웃
- 연결 종료
- 잘못된 JSON
- 정상적인 `-98` 근거리
- 경로 없음

계층 A에서 확인할 것:

- 실제 활성 요청 수가 `C`를 넘지 않는가?
- 시작 간격이 `S`보다 짧아지지 않는가?
- 시간 창 안의 요청 수가 `R`을 넘지 않는가?
- 느린 요청 하나가 전체 큐를 필요 이상으로 막는가?
- 429 이후 새 요청이 즉시 중단되는가?
- 취소 후 대기 중인 작업이 시작되지 않는가?

### 6.2 계층 B: 로컬 전체 애플리케이션

브라우저 → `/api/transit` → mock upstream의 전체 흐름을 검증한다.

확인할 것:

- UI 진행률
- 부분 성공 유지
- 계산 취소
- 장소 변경 후 stale 결과 차단
- 두 탭 또는 두 브라우저 세션의 동시 실행
- 클라이언트 스케줄러와 서버 측 스케줄러의 차이

### 6.3 계층 C: 실제 ODsay 제한 검증

계층 A와 B를 통과한 후보 2~3개만 실제 API에 적용한다.

실제 API에서 임계점을 찾을 때까지 계속 호출하지 않는다. 사전에 승인한 예산 안에서 후보의 안정성을 확인하는 방식으로만 실행한다.

## 7. 가장 중요한 구조적 에지케이스: 여러 사용자

현재 요청 큐는 브라우저의 `useTransitMatrix` 안에 있다. 한 사용자가 `C=1`이어도 사용자 두 명이 동시에 실행하면 서버에는 두 요청이 겹칠 수 있다.

```text
사용자 A 브라우저: 동시성 1
사용자 B 브라우저: 동시성 1
서버에서 본 동시성: 최대 2
```

따라서 아래를 별도로 측정한다.

| ID | 동시 사용자 | 사용자별 행렬 | 확인할 값 |
|---|---:|---:|---|
| U01 | 1 | 5 × 5 | 단일 사용자 기준 |
| U02 | 2 | 각 3 × 3 | 공유 키 기준 동시성 |
| U03 | 2 | 각 5 × 5 | 일반 부하 중첩 |
| U04 | 3 | 각 3 × 3 | 짧은 다중 사용자 폭주 |
| U05 | 1 실행 중 다른 사용자 시작 | 5 × 5 + 1 × 1 | 짧은 요청의 대기시간 |

클라이언트 측 제한만으로는 서비스 전체 호출률을 보장하지 못한다.

운영 구조 후보:

1. 클라이언트별 제한만 적용
2. Next.js 서버 인스턴스별 큐 적용
3. 공유 저장소를 이용한 서비스 전체 분산 제한

Vercel처럼 여러 서버 인스턴스가 생길 수 있는 환경에서는 메모리 기반 서버 큐도 전체 제한을 보장하지 못한다. 실제 운영에서 API 키 전체 호출률을 보장해야 한다면 분산 rate limiter가 필요하다.

## 9. 실험 순서

### 0단계: 정책과 예산 확인

- 계정 등급 확인
- 일일 호출 한도 확인
- 실제 API 실험 허용 범위 확인
- 당일 사용량 확인
- 실험 예산 확정

이 단계가 끝나기 전에는 실제 API 추가 실험을 하지 않는다.

### 1단계: 스케줄러 구현 및 단위 테스트

실험용 스케줄러가 다음 설정을 인자로 받도록 한다.

```text
concurrency
minStartGapMs
completionCooldownMs
maxStartsPerWindow
windowMs
errorCooldownMs
```

가상 시간과 mock 응답을 사용해 Q01~Q12를 자동 테스트한다.

### 2단계: mock 부하 실험

모든 Q × M 조합을 실제 API 없이 실행한다.

여기서 잘못된 후보를 제거한다.

- 설정 위반
- 중복 요청
- 누락 요청
- 큐 교착
- 취소 후 실행
- 공정성 문제

### 3단계: 다중 사용자 로컬 E2E

U01~U05를 mock upstream으로 실행한다.

클라이언트 제한만으로 충분한지, 서버 또는 분산 제한이 필요한지 판단한다.

### 4단계: 실제 API 소규모 계단식 실험

ODsay 정책과 예산 확인 후 진행한다.

느린 후보부터 시작:

```text
C=1, G=250ms
C=1, G=0ms
C=2, S=1000ms
C=2, S=750ms
C=2, S=500ms
```

각 후보를 작은 고정 경로 집합에서 반복한다. 모든 단계에서 제한 오류가 없고 예산이 남을 때만 다음 후보로 간다.

`C=2, S=250ms`와 `C=3`은 앞 단계 결과 및 ODsay 허용 범위를 확인한 뒤에만 진입한다.

### 5단계: 실제 API 일반 규모 검증

4단계에서 살아남은 후보 최대 2개만 3 × 3 및 5 × 5에 적용한다.

## 10. 후보 탈락 및 중단 조건

- 계획된 호출 예산 80% 도달

- 기준선 대비 속도 개선이 10% 미만

## 12. 최종값 선택 규칙

최종 후보는 단순히 가장 빠른 설정이 아니다.

1. 실제 API에서 429와 `-1`이 0건이어야 한다.
2. 다중 사용자 환경에서도 서비스 전체 제한이 유지되어야 한다.
3. 반복 실행과 서로 다른 시간대에서 재현되어야 한다.
4. 실패 경계 바로 아래 값은 선택하지 않는다.
5. 통과한 가장 빠른 후보보다 한 단계 보수적인 설정을 기본값으로 삼는다.
6. 운영 오류율을 관찰하면서 설정만으로 낮출 수 있어야 한다.

예시:

```text
C=2, S=500ms 통과
C=2, S=250ms 실패
→ 운영 후보는 C=2, S=500~750ms 범위
```

실험 전에는 특정 숫자를 최종값으로 미리 정하지 않는다.

- 최대 활성 요청 2개
- 요청 시작 간격 최소 500ms
- 최근 1초 시작 요청 최대 2개
- 활성 슬롯이 찬 동안 다음 작업 대기
- 대기 작업 취소 후 미실행
- 429 발생 후 해당 브라우저 계산의 대기 셀 중단
- 부분 결과와 행렬 크기 보존

### 17.4 배포 구조상 남은 제한

1차 반영 당시 서버 큐는 **Next.js 서버 인스턴스 하나 안에서만** `C2/S500/R2`를 공유했다. Vercel이 여러 인스턴스를 동시에 실행하면 각 인스턴스가 별도 메모리 큐를 가지므로 API 키 전체 기준 호출률은 이 값보다 커질 수 있다.

따라서 1차 반영의 범위는 다음과 같았다.

```text
브라우저 한 개: C2/S500
서버 인스턴스 한 개: C2/S500/R2
배포 전체 여러 인스턴스: 아직 보장하지 않음
```

배포 전체의 엄격한 제한이 필요하면 Redis 등 공유 저장소를 사용하는 분산 limiter를 후속으로 적용해야 한다.

## 18. C·S 공정 비교 재실험 계획

### 18.1 재실험 이유

16절의 후보 비교는 설정별 반복 횟수와 다중 세션 조건이 같지 않았다. 따라서 `C2/S500`을 1차 운영 후보로 고른 판단에는 실험 결과뿐 아니라 별도로 정한 안전 여유가 섞여 있었다.

이번 재실험에서는 안전 여유를 사후에 임의로 적용하지 않고, 동일한 조건에서 측정한 결과로 C와 S를 선택한다.

### 18.2 비교 후보와 고정 조건

비교 후보:

```text
C2/S500
C3/S500
C2/S250
C3/S250
```

모든 후보에 동일하게 적용할 조건:

- 단일 세션: 5 × 5, 3회 반복, 후보별 75요청
- 다중 세션: 두 세션이 각각 3 × 3, 2회 반복, 후보별 36요청
- 후보별 총 111요청
- 전체 추가 요청 예산: 444요청
- 2026-07-29 기존 사용량 283요청을 포함한 예상 누적: 727/1,000
- 반복 사이 냉각시간: 5초
- 자동 재시도: 없음
- 실행 순서: 느린 후보에서 빠른 후보 순

### 18.3 중단 조건

다음 중 하나라도 발생하면 해당 실행과 이후의 더 빠른 후보를 중단한다.

- HTTP 429
- ODsay `-1`
- HTTP 5xx 또는 네트워크 오류가 연속 3회
- 예상 누적 호출량 800회 도달
- 계획하지 않은 중복 요청

### 18.4 최고 성능 후보 선택 규칙

1. 예정된 단일·다중 세션 실행을 모두 완료한 후보만 비교한다.
2. 429, ODsay `-1`, 5xx, 네트워크 오류가 한 건이라도 있으면 탈락시킨다.
3. 설정한 최대 동시성과 최소 시작 간격을 위반한 후보는 탈락시킨다.
4. 통과 후보별로 단일 세션 평균 완료시간과 다중 세션 평균 완료시간을 계산한다.
5. 각 부하군의 최단 평균을 1로 둔 정규화 시간의 평균이 가장 낮은 후보를 선택한다.
6. 동점이면 동시성이 낮은 후보, 그다음 시작 간격이 긴 후보를 선택한다.

이 규칙에서 선택된 값은 “ODsay의 최대 허용치”가 아니라 **이번에 동일 조건으로 검증한 후보 중 가장 빠른 값**으로 표현한다.

### 18.5 실제 실행 결과

2026-07-29에 배포 서비스 `https://moduspot.vercel.app/api/transit`를 대상으로 계획한 444요청을 모두 실행했다.

| 후보 | 요청 | 성공 | 오류 | 5 × 5 단일 평균 | 두 세션 3 × 3 평균 | 실제 최대 C | 실제 최소 S | 최근 1초 최대 시작 | 선택 점수 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| `C2/S500` | 111 | 111 | 0 | 13.632초 | 9.473초 | 2 | 500ms | 2 | 1.775 |
| `C3/S500` | 111 | 111 | 0 | 12.784초 | 9.072초 | 3 | 500ms | 2 | 1.682 |
| `C2/S250` | 111 | 111 | 0 | 8.051초 | 5.747초 | 2 | 250ms | 4 | 1.062 |
| `C3/S250` | 111 | 111 | 0 | 7.444초 | 5.510초 | 3 | 250ms | 4 | 1.000 |

오류 집계:

```text
HTTP 429        0
ODsay -1        0
HTTP 5xx        0
네트워크 오류   0
누락 요청       0
```

기존 실험 283요청과 이번 공정 비교 444요청을 합친 당일 누적은 727/1,000이다.

### 18.6 변수별 효과

S를 500ms에서 250ms로 줄인 효과가 가장 컸다.

| 고정한 C | 단일 세션 단축 | 다중 세션 단축 |
|---|---:|---:|
| `C=2` | 40.9% | 39.3% |
| `C=3` | 41.8% | 39.3% |

C를 2에서 3으로 늘린 효과는 S 변경보다 작지만 두 부하군에서 일관되게 나타났다.

| 고정한 S | 단일 세션 단축 | 다중 세션 단축 |
|---|---:|---:|
| `S=500ms` | 6.2% | 4.2% |
| `S=250ms` | 7.5% | 4.1% |

따라서 이번 후보 범위에서는 `S=250ms`가 전체 시간 단축의 주된 원인이며, `C=3`이 추가로 4~8%를 단축했다.

### 18.7 실험상 최고 성능 C·S

이번에 동일 조건으로 검증한 후보 중 최고 성능값은 다음과 같다.

```text
최대 동시 요청 C = 3
최소 요청 시작 간격 S = 250ms
응답 완료 후 추가 대기 G = 0ms
최근 1초 최대 요청 시작 R = 4
```

최고 성능 판단 근거:

1. 후보별 111요청으로 조건을 동일하게 맞췄다.
2. `C3/S250`의 111요청이 모두 성공했고 429, ODsay `-1`, 5xx 및 네트워크 오류가 없었다.
3. 단일 세션 5 × 5와 두 세션 3 × 3에서 모두 평균 완료시간이 가장 짧았다.
4. 사전에 정한 정규화 선택 점수가 `1.000`으로 가장 낮았다.
5. 실제 최대 동시성 3과 최소 시작 간격 250ms가 관측되어 설정이 명목상 값에 그치지 않았다.
6. `C2/S250`과 비교해 단일 세션 7.5%, 다중 세션 4.1% 추가 단축됐다.

이 결과는 ODsay가 동시 요청 3개 또는 250ms 간격을 공식적으로 보장한다는 뜻이 아니다. **실제로 같은 조건으로 비교한 네 후보 중 `C3/S250`이 가장 빨랐고 이번 111요청에서 오류가 없었다**는 범위의 결과다. ODsay의 공개되지 않은 최대 허용치를 의미하지 않는다.

### 18.8 안정형 운영 C·S 결론

운영 기본값은 최고 성능값을 그대로 사용하지 않고, 초당 호출량과 반복 편차를 함께 고려해 다음과 같이 정한다.

```text
최대 동시 요청 C = 3
최소 요청 시작 간격 S = 500ms
응답 완료 후 추가 대기 G = 0ms
최근 1초 최대 요청 시작 R = 2
```

운영값 결정 근거:

1. `C3/S500`도 동일 조건 111/111요청에 성공했고 제한 및 기타 오류가 없었다.
2. ODsay가 공개한 제한 형태는 서비스 유형별 초당 호출 건수이므로 동시성 C보다 시작률을 정하는 S와 R이 직접적인 보호 장치다.
3. `S=500ms`는 실제 최근 1초 시작량을 최대 2회로 유지했다. `S=250ms`의 최대 4회보다 절반이다.
4. 단일 5 × 5 반복 완료시간이 12.836초, 12.762초, 12.753초로 네 후보 중 편차가 가장 작았다.
5. `C2/S500`과 시작률은 같지만 단일 세션 6.2%, 다중 세션 4.2% 빨랐다.
6. C=3은 응답이 느릴 때 빈 슬롯을 활용하지만 S=500ms와 R=2 때문에 새 요청 시작률을 높이지 않는다.

따라서 두 값을 다음처럼 구분한다.

```text
실험상 최고 성능값 = C3/S250/R4
안정형 운영 기본값 = C3/S500/R2
```

### 18.9 제품 반영

브라우저 계산 큐와 Next.js 서버 인스턴스 큐의 기본값을 안정형 운영값에 맞춰 변경했다.

```text
TRANSIT_SERVER_MAX_CONCURRENCY=3
TRANSIT_SERVER_MIN_START_GAP_MS=500
TRANSIT_SERVER_MAX_STARTS_PER_WINDOW=2
TRANSIT_SERVER_RATE_WINDOW_MS=1000
```

429 또는 ODsay `-1` 발생 시 해당 계산의 대기 요청을 중단하고 자동 재시도하지 않는 기존 보호 동작은 유지한다. Vercel 다중 인스턴스 전체의 호출률을 하나로 묶으려면 여전히 공유 저장소 기반 분산 limiter가 필요하다.

### 18.10 최종 자동화 검증

안정형 운영값 `C3/S500/R2`를 반영한 뒤 다음 검증을 통과했다.

- ESLint 전체 통과
- 단위 테스트 50개 통과
- 프로덕션 빌드 및 TypeScript 검사 통과
- 브라우저 E2E 5개 통과
- E2E에서 네 요청을 동시에 대기시켜 시작 간격 500ms와 최대 활성 요청 3개 확인
- 429 발생 후 대기 셀 중단 및 완료 결과 보존 확인

브라우저 E2E는 API 응답을 가로채는 mock 방식으로 실행해 ODsay 일일 호출량을 추가로 사용하지 않았다.

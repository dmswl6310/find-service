## 다음 실행부터 적용할 예산

Basic 현재 일일 한도 30회. 날짜가 바뀌었다는 이유만으로 한도 회복을 가정하지 않는다. 최신 사용자 지시에 따라 매일 시작 사용량0건을 사용하며 재질문하지 않는다. 당일 원장의 이미 시도한 호출과 예약을 합산한다.

하루 실험은 기본 3x3 두 배치, 최대 18요청으로 제한한다. 서비스의 다른 호출과 모든 실험 실행의 시도 수를 합산하고 남은 한도를 넘지 않는다. 실패·취소된 호출도 보수적으로 합산한다. 기본적으로 최소 12회는 실험 외 사용 여유로 남긴다. 남은 한도가 부족하면 줄이거나 그날은 건너뛴다.

## 일별 비교 방식

1. 상한 없는 직접 호출과 동일한 9개 장소 조합을 유지한다. 실제 fetch 시작·종료와 최대 동시 수를 기록한다.
2. 다음 후보는 250ms 대 125ms. 첫날 A/B, 다음 실행일 B/A로 순서를 뒤집는다. 날짜별 외부 상태 차이를 기록하고 동일 날짜 안의 차이도 비교한다.
3. 두 순서 모두 정상이고 속도 개선이 확인되면 125ms 대 63ms 같은 다음 후보를 별도 날짜에 검토한다. 실패 경계를 강제로 찾는 실험은 하지 않는다.
4. 유망 후보를 좁힌 뒤 500ms 기준선과 반복 비교한다. 후보별 최소 4배치가 쌓이도록 날짜와 순서를 균형 배치한다.
5. 정상 결과 25개가 필요한 5x5 확인은 18회 일별 예산 안에 들어가지 않는다. 자동 실행하지 말고 그날 다른 호출량과 예산 조정 또는 허용 한도 확보를 먼저 판단한다. 2세션 3x3은 18개 요청이므로 확인된 예산 안에서 별도 날짜에 진행 가능하다.
6. 매일 원본 JSON을 날짜별 디렉터리에 새로 저장하고 이 파일 및 전체 매트릭스에 실행일, 간격, 배치/사용자 수, 성공/시도, 시간, 오류 코드, 중단 이유를 추가한다. 과거 원본과 잘못된 초기 가정의 정정 기록을 삭제하지 않는다.

## 오류와 재개

- HTTP 429, 본문 code=429 또는 -1 감지 시 새 호출과 더 빠른 후보를 즉시 멈춘다. 이미 시작한 호출은 집계한다.
- 일일 한도 소진이면 몇 분 대기로 재개하지 않는다. 한도 회복/남은 양을 확인한 다음 예정 실행에서 재개한다.
- 초당 제한으로 확인되는 경우에도 동일 후보 자동 재시도 금지. 제공자 재개 지침과 사용량을 확인하고 다음 날짜의 느린 기준값부터 검토한다.
- 입력·인증·경로 오류, 네트워크·타임아웃은 원인을 분류하고 성능 비교를 보류한다. 실패로 빨리 끝난 배치를 속도 개선으로 취급하지 않는다.

## 실행 도구 상태

기존 transit-direct-experiment.mjs는 2026-10-06 전용이므로 일별 실행에 사용하지 않는다. 2026-10-07에 scripts/transit-daily-experiment.mjs와 scripts/transit-daily-policy.mjs를 준비했다. 현재 사용자/콘솔 사용량 증거가 같은 한국 날짜이고 1시간 이내인지 확인하며 12회 여유를 보존하고 최대18회만 예약한다. 일별 잠금·기존 원장 중복 거부·발송 전 예약 기록·모든 오류 중단을 적용한다. 날짜별 도구의 확인 옵션은 --used, --confirmed-at, --source, --gaps이며 실제 확인 없이 임의로 값을 채우지 않는다. 어제 quota-exhausted 상태는 보존하고 오늘 별도 원장을 사용한다. 키는 .env.local에서만 읽고 출력하지 않는다.

최종 선택 또는 추가 계정 권한·사용자 확인이 필요한 경우 알려준다. 상태가 그대로라면 반복 알림을 보내지 않는다.
